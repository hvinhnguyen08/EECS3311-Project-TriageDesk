# Changes from the Stage 1 design

A running record for Section 4 of the Stage 2 report, written as
Original design -> Implemented change -> Reason -> Impact.

| # | Original design (Stage 1) | Implemented change | Reason | Impact |
|---|---|---|---|---|
| C1 | `Finding.severity` and `Case.severity` are `String` | `Severity` enum (LOW, MEDIUM, HIGH, CRITICAL) with a weight and `fromWazuhLevel()` | Case severity is "the highest of its findings" and priority depends on severity; both need a reliable ordering that strings do not give | `Finding`, `Case`, detectors (F03), `CaseManager.computePriority` (F05). No pattern affected. |
| C2 | `TriageVerdict.verdict` is `String` | `Verdict` enum (TRUE_POSITIVE, FALSE_POSITIVE, BENIGN, NEEDS_REVIEW) with lenient `parse()` | Model output must be validated; any unknown value becomes NEEDS_REVIEW, as F06 specifies | `TriageVerdict`, `SocAgent.triage` (F06), `recommendResponse` (F10). |
| C3 | Value classes with private fields | `SecurityEvent`, `Finding`, `Ioc`, `AttackTechnique`, `TriageVerdict`, `AgentResult`, `DashboardStats` are Java records (immutable); `Case` and `ResponsePlan` stay mutable classes | Immutable evidence cannot be changed after import; less boilerplate. Accessors are `id()` rather than `getId()` | Domain package only. Same fields as the class diagram. |
| C4 | `Ioc.score : int` | Same, plus `Ioc.UNAVAILABLE = -1` and `withScore()` | F07 requires a "score unavailable" result when a provider fails | `EnrichmentService`, adapters (F07). |
| C5 | `Case` has no creation time or clock | `Case.createdAt` and an injectable `Clock`; `recordHistory()` is public | The timestamps of history entries and notes must be testable, and the State classes (in another package) record transitions in the history | `Case`, `CaseState` subclasses (F09). |
| C6 | `SecurityEvent` has no event type or format-specific fields | Added `category` (auth_failure, auth_success, privilege, web_request, alert, other), an `attributes` map (HTTP status, path, user agent, sudo command, Wazuh groups...) and a `Builder` | Detectors must work on events from any format: BruteForceDetector needs "failed login" whether it came from auth.log or Wazuh, and WebScanDetector needs the HTTP status, which the Stage 1 fields cannot hold | `SecurityEvent`, all parsers (F01, F02), detectors (F03), `EventStore.search/countBy` and the agent tools (F04, F06, F12). |
| C7 | `EventStore.addEvents` appends; search criteria not specified | Re-importing the same file (batch) replaces its earlier events; `search` accepts the event fields plus `text`, `since`, `until`, `minLevel` and rejects unknown keys with a message listing the allowed ones; added `batchIds()` | Prevents duplicate events and duplicate findings when a file is imported twice; clear errors let the agent correct a bad tool call; `batchIds()` feeds the imported-file list (F04) | `EventStore` (F01, F02, F04, F12, F13), `SearchEventsTool`, `CountByTool`. |
| C8 | auth.log lines get "the file's year" | The current year is assumed, and a date more than a day in the future is moved to the previous year | The parser receives lines, not the file; the rollback handles a December log imported in January | `AuthLogParser` (F02). |
| C9 | Unsupported format reported as an error message | `UnsupportedFormatException` (an `IllegalArgumentException`) thrown by `detectFormat`/`createParser`; `LogParserFactory.readLines()` reads UTF-8 leniently and removes a byte-order mark | The GUI and CLI can catch one exception type and show "Unsupported file format"; real logs often contain invalid bytes | `LogParserFactory`, `SocAssistant.importFile` (F01, F02). |
| C10 | `Detector` has only `detect()`; `DetectionEngine` has `register()` and `runAll()`; thresholds are detector attributes | Added `Detector.name()`, `DetectionEngine.getLastErrors()` and `DetectionEngine.withStandardDetectors(AppConfig)`; thresholds are read from `.env` (`DETECT_*`); `SuccessAfterFailureDetector` also has a time window (default 10 minutes) | F03 says "a detector that fails is skipped": the engine needs the detector's name to report which one failed. "Thresholds are configurable" needed a concrete mechanism. A success after failures from days earlier is not suspicious, so a window is needed | `detect` package (F03), `AppConfig`. Strategy pattern unchanged. |
| C11 | Detectors read all events | `BruteForceDetector` and `SuccessAfterFailureDetector` count only raw log events, not Wazuh alerts | Wazuh already summarises failed logins in its own brute-force alert (rule 5763), which `WazuhAlertDetector` reports; counting the alerts too would double-count when both the alerts and auth.log are imported | `BruteForceDetector`, `SuccessAfterFailureDetector` (F03). |
| C12 | `CaseManager` saves `Case` objects as JSON; grouping rule "same source IP or host within 60 minutes" | `Case.Snapshot` record with `Case.snapshot()` / `Case.fromSnapshot()` is what is saved; grouping uses the source IP when a finding has one and the host only when it has none; added `CaseManager.load()` and `getWarnings()`; re-detected findings (same detector and evidence) are ignored | `Case` is mutable and holds a clock, so a plain record keeps JSON concerns out of the domain class and restores a case without adding history. Grouping by host for every finding would merge unrelated attacks on the same server into one case. Running Detect twice must not duplicate findings | `Case`, `CaseManager` (F05), and later F06–F11, which save cases. |
| C13 | `CaseState` with `startInvestigation/escalate/close/reopen/name`; `CaseManager.applyAction(caseId, action, comment)` | Added `CaseState.allowedActions()`, `isClosed()` and `fromName()`; refused actions throw `InvalidTransitionException` naming the allowed actions; `Case` stores the analyst's `resolution` (TRUE_POSITIVE, FALSE_POSITIVE or BENIGN) and `isClosed()`; an `applyAction(caseId, action, resolution, comment)` overload handles close; action names are in `CaseActions`; reopening returns to INVESTIGATING; closed cases never absorb new findings | UC07 requires "an error explaining the allowed actions" and F09 "closing as true or false positive", which needs somewhere to keep the resolution; saved cases must restore their state; F05 says findings join an *open* case | `casemgmt` package, `Case` (F09, F05), GUI status buttons and CLI `status` command (commit 6). State pattern as designed. |
| C14 | auth.log lines are read in "the file's" time zone (unspecified) | New setting `LOG_TIMEZONE` (default UTC); `LogParserFactory(ZoneId)` passes it to `AuthLogParser` | Syslog lines carry no time zone. Using the PC's zone put auth.log events hours away from the same activity in Wazuh alerts (which carry UTC offsets), so related findings landed in different cases | `AppConfig`, `LogParserFactory`, `AuthLogParser` (F02, F05). |
| C15 | `SocAssistant.importFile` returns `int`; `runDetections` returns `List<Case>`; `changeStatus(caseId, action, comment)`; facade builds the agent's `ToolRegistry` | `importFile` returns `ImportResult` (batch ID, format, imported, skipped); `runDetections` returns `DetectionResult` (findings, cases, warnings); `changeStatus` overload with a resolution for close; added `listBatches()` and `SocAssistant.create(AppConfig[, dataDir])`, which builds and loads the subsystems (the agent parts are added in later commits) | F01 must report imported and skipped lines; F03 must report failed detectors and "No suspicious activity"; F09 close needs a resolution (C13); the imported-file list feeds F04 | `SocAssistant`, `TriageDeskCli` and later the GUI controllers. Facade pattern as designed. |
| C16 | CLI commands: import, detect, summarize, enrich, map, triage, status, note, respond, report, ask, stats | Added `cases` (list the queue) and `show CASE_ID` (case details); `--data-dir` option; errors printed as one line with exit code 1; `triagedesk.cmd` / `./triagedesk` launchers for the shaded jar | The Stage 1 CLI had no way to see the case list or a case's details after `detect`, which the GUI shows in its case list and case view | `TriageDeskCli` (F05, F09). The AI commands are added with their features. |
| C17 | `LlmClient.chat(messages : List<String>, toolSpecs : List<String>) : LlmReply`; `LlmReply` has one `toolName`/`toolArgs` | `chat(List<ChatMessage>, List<String>)` with a new `ChatMessage` record (role, content, tool calls, tool-call ID) and `ToolCall` record; `LlmReply` holds a list of tool calls plus prompt/completion token counts; added `LlmClient.describe()` and `LlmException`; `OpenAiClient` works with any OpenAI-compatible service (OpenAI, Groq, OpenRouter, Ollama) via `LLM_BASE_URL`; `MockLlmClient` takes scripted replies and an optional responder function; new `LLM_TIMEOUT_SECONDS` setting | The function-calling protocol needs assistant messages that carry tool calls and tool messages linked to them by ID, which plain strings cannot represent; models may request several tools in one reply; token counts are needed to report AI usage; one exception type lets the GUI and CLI show "AI service unavailable" | `agent` package; `SocAgent.runLoop` (commit 8); SD03 and SD05 should show `ChatMessage`. Strategy pattern (`SocAgent` -> `LlmClient`) as designed. |
| C18 | `Tool` has `name()`, `description()`, `execute(argsJson)`; `ToolRegistry` has `register`, `get`, `specs`; `SocAgent.runLoop` stops at 6 steps | `Tool` also has `parameters()` (the JSON Schema the model needs to call it correctly); `ToolRegistry` gained `has()` and `names()`; at the step limit the agent asks the model once more without tools for its best answer and marks the result `stoppedEarly`; a tool that is not allowed for the task is refused with an error result; tool results over 6000 characters are cut; `search_events` returns the total count plus up to `limit` (default 20, max 50) compact events, `count_by` returns the top groups (default 10) with totals | Function calling requires an argument schema per tool; F04/F12 specify a "partial answer marked incomplete" at the step limit, which needs a final answer to show; restricting tools per task (Stage 1 4.7) must hold even if the model asks for another tool; free-tier models have small context windows | `agent` package (F04, F06, F12). Command pattern as designed: `SocAgent` is the invoker, `EventStore` the receiver. |
